# Как разбирать OOMKilled и нехватку памяти

[[00 Linux - вопросы]]

`OOMKilled` означает, что процесс был убит из-за нехватки памяти. В Kubernetes это часто видно в статусе контейнера, в Linux - через сообщения ядра.

Проверки на Linux:
```bash
# Показывает использование RAM и swap.
# Ожидаемо: видно, сколько памяти available и используется ли swap.
free -h

# Ищет OOM-события в сообщениях ядра.
# Ожидаемо: строки вида Out of memory и Killed process, если OOM был.
dmesg | grep -i oom

# Ищет OOM-события в kernel-журнале systemd.
# Ожидаемо: сообщения ядра о нехватке памяти и убитых процессах.
journalctl -k | grep -i oom

# Показывает процессы, отсортированные по потреблению памяти.
# Ожидаемо: сверху процессы с максимальным %MEM.
ps aux --sort=-%mem | head
```

Проверки в Kubernetes:
```bash
# Показывает подробное состояние pod, включая last state и reason.
# Ожидаемо: в Events или Container State можно увидеть OOMKilled.
kubectl describe pod <pod>

# Показывает логи предыдущего экземпляра контейнера после рестарта.
# Ожидаемо: последние сообщения приложения перед падением.
kubectl logs <pod> --previous

# Показывает текущее потребление CPU/RAM pod'ами.
# Ожидаемо: таблица pod, CPU(cores), MEMORY(bytes), если metrics-server работает.
kubectl top pod
```

Что выяснить:
- сколько памяти потребляет процесс;
- есть ли memory leak;
- какие лимиты выставлены;
- не слишком ли маленький limit;
- есть ли рост памяти со временем;
- не убивает ли приложение spike нагрузки.

Короткий ответ:

Я бы подтвердил OOM через `dmesg` или `kubectl describe`, посмотрел потребление памяти, лимиты и динамику роста. Дальше решал бы: увеличивать limit, оптимизировать приложение или искать утечку.
