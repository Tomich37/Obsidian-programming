# Linux

## 1. Насколько глубоко знаешь Linux

Я оцениваю знания как уверенный базовый/средний уровень. Умею работать в консоли, смотреть процессы, логи, сетевые соединения, диски, права, systemd-сервисы. Приходилось заходить на серверы по SSH, диагностировать проблемы, смотреть `top`, `htop`, `df`, `du`, `journalctl`, `systemctl`, `ss`, `iostat`.

Глубокий kernel-level опыт пока не заявляю, но понимаю базовые сущности: процессы, потоки, файловые системы, inode, swap, systemd, сетевой стек.

## 2. Как оценить сколько ресурсов потребляет сервис

Сначала понять, как сервис запущен:
```bash
systemctl status <service>
ps aux | grep <service>
```

Дальше смотреть ресурсы:
```bash
top
htop
ps -o pid,ppid,%cpu,%mem,rss,vsz,cmd -p <PID>
```

Если это systemd-сервис:
```bash
systemctl status <service>
journalctl -u <service> -f
```

По диску:
```bash
iostat -x 2 3
iotop
```

По сети:
```bash
ss -tulnp
```

Если сервис в контейнере:
```bash
docker stats
docker logs -f <container>
```

## 3. top и htop. Какие показатели есть

`top` и `htop` показывают состояние системы и процессов.

Основные показатели:
- `CPU` - загрузка процессора;
- `MEM` - использование оперативной памяти;
- `SWAP` - использование swap;
- `PID` - идентификатор процесса;
- `USER` - пользователь процесса;
- `%CPU` - сколько CPU ест процесс;
- `%MEM` - сколько памяти ест процесс;
- `TIME` - сколько CPU-времени уже использовал процесс;
- `COMMAND` - команда/процесс;
- `Load Average` - средняя очередь задач за 1, 5 и 15 минут.

## 4. Какая есть разная память в htop

В `htop` обычно видно:
- used memory - реально занятая память;
- buffers - буферы ядра для операций ввода-вывода;
- cache - файловый кеш, который Linux может освободить при необходимости;
- swap - область на диске, куда выгружаются редко используемые страницы памяти.

## 5. Какие показатели оперативной памяти есть в htop

Главное смотреть не только "used", а еще cache/buffers. Linux активно использует свободную память под кеш, и это нормально. Если память занята кешем, но есть `available`, это не проблема. Проблема начинается, когда мало `available`, растет swap и процессы начинают тормозить.

## 6. Что такое LA

`Load Average` - средняя загрузка системы за 1, 5 и 15 минут. Это не просто процент CPU, а среднее количество задач, которые выполняются или ждут ресурс, например CPU или I/O.

Оценивать LA надо относительно числа CPU-ядер. Если 4 ядра и LA около 4 - система примерно полностью загружена. Если LA сильно выше количества ядер, значит задачи стоят в очереди.

## 7. Почему в LA отображается 3 цифры

Три цифры показывают среднюю загрузку за разные интервалы:
- 1 минута - что происходит прямо сейчас;
- 5 минут - краткосрочный тренд;
- 15 минут - более сглаженная картина.

Так видно, нагрузка только началась, уже проходит или держится долго.

## 8. Как посмотреть нагрузку на диск

Можно использовать:
```bash
iostat -x 2 3
iotop
```

В `iostat` полезные поля:
- `%util` - насколько диск занят;
- `r/s`, `w/s` - операции чтения/записи в секунду;
- `await` - среднее время ожидания операций.

## 9. Не можем создать файл, место есть. В чем причины

Самая частая причина - закончились inode.

Проверка:
```bash
df -h
df -i
```

`df -h` покажет место, а `df -i` покажет количество inode. Если inode заняты на 100%, новые файлы создать нельзя, даже если свободные гигабайты еще есть.

Другие причины:
- нет прав на директорию;
- файловая система смонтирована read-only;
- квоты пользователя;
- лимит файлов в директории или у процесса.

## 10. Что такое inode

`inode` - это индексная структура файловой системы, где хранится метаинформация о файле: права, владелец, размер, timestamps и ссылки на блоки данных. Имя файла хранится отдельно в директории, а директория связывает имя с inode.

Если inode закончились, файловая система не может создать новый файл.

## 11. Что такое swap

`swap` - область на диске, которую Linux использует как дополнительную память, когда не хватает RAM или нужно выгрузить редко используемые страницы. Swap медленнее оперативной памяти, потому что это диск. Небольшое использование swap не всегда проблема, но активный swap обычно означает нехватку RAM или неоптимальную нагрузку.

Проверить:
```bash
free -h
swapon --show
```

## 12. Чем отличается кеш от буфера

Кеш - это данные файлов, которые Linux держит в памяти, чтобы быстрее читать их повторно.

Буфер - это память для операций ввода-вывода, например блоки, которые готовятся к записи или чтению с устройства.

Проще: cache ближе к содержимому файлов, buffers ближе к служебным данным блочных устройств и операциям I/O.

## 13. Что такое systemd

`systemd` - это система инициализации и менеджер сервисов в современных Linux. Это процесс с PID 1, который запускает остальные службы, следит за их состоянием, управляет зависимостями, логами через `journald`, автозапуском и target'ами.

Основные команды:
```bash
systemctl status <service>
systemctl start <service>
systemctl restart <service>
systemctl enable <service>
journalctl -u <service>
```

## 14. Процессы и потоки. В чем различие

Процесс - отдельный экземпляр программы со своим адресным пространством, PID, ресурсами.

Поток - единица выполнения внутри процесса. Потоки одного процесса разделяют память и ресурсы процесса, но имеют свой стек и контекст выполнения.

Проще: процессы более изолированы, потоки легче и быстрее взаимодействуют, но ошибка в одном потоке может повлиять на весь процесс.

## 15. Hardlink и symlink

`Hardlink` - еще одно имя для того же inode. Файл и hardlink равноправны. Пока есть хотя бы одна hardlink-ссылка, данные остаются на диске.

`Symlink` - отдельный файл-ссылка, который хранит путь к другому файлу. Если оригинал удалить или переместить, symlink станет битым.

Команды:
```bash
ln file hardlink
ln -s file symlink
ln -sf file symlink
```

# Сети

## 1. Есть ли опыт работы по сетям

Есть базовый практический опыт: SSH-доступ, проверка портов, диагностика доступности, понимание TCP/UDP, IP, DNS, NAT, подсетей. Из команд использовал `ping`, `traceroute`, `ss`, `telnet`/`nc`, `ip a`, `ip route`, `nslookup`/`dig`.

## 2. Как ребенку объяснить SSH

SSH - это безопасный способ зайти на другой компьютер через сеть и получить там консоль. Как будто я сижу за своим ноутбуком, но команды выполняются на сервере.

Упрощенно:
1. Я пишу `ssh user@server`.
2. Клиент подключается к серверу на порт SSH.
3. Сервер проверяет, кто я: по паролю или ключу.
4. Если проверка прошла, открывается удаленная командная строка.
5. Все данные между мной и сервером шифруются.

## 3. Можно ли заходить по SSH не по паролю

Да, по SSH-ключам.

Генерируем пару ключей:
```bash
ssh-keygen
```

Публичный ключ кладем на сервер в:
```bash
~/.ssh/authorized_keys
```

После этого сервер проверяет не пароль, а то, что у клиента есть приватный ключ.

## 4. Что такое порт

Порт - это номер входа в конкретное приложение на хосте. IP-адрес приводит нас к серверу, а порт - к нужному сервису на этом сервере.

Аналогия: IP - адрес здания, порт - номер кабинета. В одном здании может быть много кабинетов: SSH на 22, HTTP на 80, HTTPS на 443.

## 5. Что такое NAT

`NAT` - преобразование сетевых адресов. Обычно используется, чтобы много устройств из локальной сети выходили в интернет через один внешний IP.

Пример: ноутбуки имеют адреса `192.168.1.x`, а наружу выходят через роутер с одним публичным адресом. Роутер запоминает, кто какой запрос отправил, и возвращает ответы правильному устройству.

## 6. Чем TCP отличается от UDP

`TCP` - надежный протокол с соединением. Он гарантирует доставку, порядок данных и повторную отправку при потере. Используется для SSH, HTTP(S), БД.

`UDP` - быстрый протокол без установления соединения и без гарантий доставки. Используется там, где важна скорость и допустимы потери: DNS, видео, голос, игры.

## 7. Что такое подсеть

Подсеть - часть IP-сети, объединенная общей маской. По IP-адресу и маске хост понимает, находится адрес назначения в его локальной сети или пакет нужно отправлять на шлюз.

## 8. Есть ли нотация для подсетей. Размер сети всегда одинаков?

Да, обычно используют CIDR-нотацию:
```text
192.168.1.0/24
10.0.0.0/16
```

Число после `/` показывает, сколько бит отведено под сетевую часть. Размер сети не всегда одинаков: чем меньше число после `/`, тем больше адресов в подсети.

## 9. Разница между /16 и /24

`/24` - 256 адресов, обычно 254 usable-адреса для хостов.

Пример:
```text
192.168.1.0/24 -> 192.168.1.0 - 192.168.1.255
```

`/16` - 65536 адресов, намного больше сеть.

Пример:
```text
192.168.0.0/16 -> 192.168.0.0 - 192.168.255.255
```

# Docker

## 1. Какой сложности делал Dockerfile

Можно отвечать так:

Писал и правил Dockerfile для сервисов: выбирал базовый образ, копировал код, ставил зависимости, задавал рабочую директорию, переменные окружения, команду запуска. Также работал с docker-compose для локального запуска нескольких сервисов.

Если честно про уровень:

Сложные production Dockerfile с большим количеством оптимизаций писал не постоянно, но понимаю основные best practices: уменьшать слои, использовать `.dockerignore`, фиксировать версии, не запускать приложение от root, отделять build-time зависимости от runtime.

## 2. Сколько строк было в сложном Dockerfile

Лучше не привязываться к числу как к показателю сложности:

В среднем Dockerfile был не очень большой, примерно 20-40 строк. Но сложность Dockerfile не всегда в количестве строк, а в том, как он собирает зависимости, кеширует слои, разделяет build и runtime, работает с секретами и пользователем.

## 3. Контейнеризация vs виртуализация

Виртуализация запускает полноценную виртуальную машину со своей ОС и ядром через гипервизор.

Контейнеризация использует общее ядро хоста, а изоляция делается через механизмы Linux: namespaces, cgroups, файловые слои.

Контейнеры легче и быстрее стартуют, но изоляция у ВМ обычно сильнее.

## 4. Best practices для Dockerfile на 100 строк

Что бы предложил:
- использовать `.dockerignore`, чтобы не тащить мусор в build context;
- объединить связанные `RUN`, чтобы не плодить лишние слои;
- ставить только нужные пакеты и чистить кеш пакетного менеджера;
- фиксировать версии базовых образов и зависимостей;
- использовать multi-stage build;
- не хранить секреты в образе;
- запускать приложение не от root;
- сначала копировать файлы зависимостей, потом код, чтобы лучше работал кеш;
- проверять размер образа и убирать ненужные build-зависимости.

## 5. Init container

`Init container` - это контейнер в Kubernetes, который запускается до основного контейнера в Pod. Он должен успешно завершиться, и только после этого стартуют основные контейнеры.

Примеры:
- дождаться доступности БД;
- выполнить миграции;
- скачать конфиг;
- подготовить файлы или права на volume.

# Kubernetes

## 1. Опыт с Kubernetes

Промышленного глубокого опыта пока немного, но дома и в учебных стендах разбирал базовые сущности: Pod, Deployment, Service, ConfigMap, Secret, Ingress, Helm. Писал манифесты, применял через `kubectl apply`, смотрел состояние через `kubectl get/describe/logs`, заходил в pod через `kubectl exec`, делал `port-forward`.

## 2. kubectl apply. Что происходит в Kubernetes

Коротко:

`kubectl apply -f manifest.yaml` отправляет YAML в Kubernetes API Server. API Server валидирует объект, сохраняет желаемое состояние в `etcd`. Дальше контроллеры видят, что желаемое состояние отличается от фактического, и начинают приводить кластер к нужному виду.

Для Deployment:
1. `kubectl` отправляет манифест в API Server.
2. API Server проверяет права, схему и сохраняет объект в `etcd`.
3. Deployment Controller видит новый Deployment и создает ReplicaSet.
4. ReplicaSet Controller создает нужное количество Pod.
5. Scheduler выбирает ноду для Pod с учетом ресурсов и ограничений.
6. Kubelet на выбранной ноде видит назначенный Pod.
7. Kubelet через container runtime, например containerd, скачивает образ и запускает контейнеры.
8. kube-proxy и CNI обеспечивают сетевую часть.

## 3. Какие сущности есть кроме Pod

Основные:
- `Deployment` - управляет репликами и обновлениями;
- `ReplicaSet` - поддерживает нужное количество Pod;
- `Service` - стабильный сетевой доступ к Pod;
- `ConfigMap` - конфигурация;
- `Secret` - секреты;
- `Namespace` - логическое разделение;
- `Ingress` - входящий HTTP/HTTPS-доступ;
- `PersistentVolume` и `PersistentVolumeClaim` - постоянное хранилище;
- `Job` и `CronJob` - разовые и периодические задачи;
- `StatefulSet` - stateful-приложения;
- `DaemonSet` - по одному Pod на каждую ноду.

## 4. ConfigMap

`ConfigMap` хранит неконфиденциальную конфигурацию: переменные окружения, параметры приложения, конфиги.

Его используют, чтобы не зашивать настройки в образ контейнера. Один и тот же образ можно запускать в разных окружениях с разными ConfigMap.

## 5. Service

`Service` дает стабильную точку доступа к Pod. Pod могут пересоздаваться и менять IP, а Service остается постоянным и направляет трафик на подходящие Pod по labels/selector.

Типы:
- `ClusterIP` - доступ внутри кластера;
- `NodePort` - доступ через порт на нодах;
- `LoadBalancer` - внешний балансировщик в облаке;
- `ExternalName` - DNS-алиас на внешний сервис.

## 6. Как дать доступ к Pod

Варианты:
- внутри кластера - `Service` типа `ClusterIP`;
- снаружи через ноду - `NodePort`;
- через облачный балансировщик - `LoadBalancer`;
- для HTTP/HTTPS - `Ingress`;
- для себя временно - `kubectl port-forward`;
- зайти внутрь контейнера - `kubectl exec -it <pod> -- /bin/bash`.

Пример:
```bash
kubectl port-forward pod/<pod> 8080:80
kubectl exec -it <pod> -- /bin/bash
```

## 7. Ingress

`Ingress` - объект Kubernetes для управления входящим HTTP/HTTPS-трафиком в кластер. Он позволяет по домену и пути направлять запросы на разные Service.

Важно: сам Ingress - это только правило. Чтобы оно работало, в кластере должен быть Ingress Controller, например nginx-ingress, Traefik или HAProxy Ingress.

Пример:
```text
site.ru/api -> backend-service
site.ru     -> frontend-service
```

## 8. NetworkPolicy

`NetworkPolicy` - правила сетевого доступа между Pod. По умолчанию в Kubernetes часто все Pod могут ходить друг к другу. NetworkPolicy позволяет ограничить, кто к кому может подключаться.

Пример применения:
- разрешить backend ходить в database;
- запретить доступ к database всем остальным;
- разрешить входящий трафик только из нужного namespace.

Важно: NetworkPolicy работает, если CNI-плагин ее поддерживает, например Calico или Cilium.

## 4. Handler в Ansible

Handler - это задача, которая запускается только если ее вызвали через `notify`, и только если основная задача что-то изменила.

Типичный пример: скопировали новый конфиг Nginx - только тогда перезапускаем или reload'им Nginx.

```yaml
tasks:
  - name: Обновить конфиг
    template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify:
      - Перезапустить Nginx

handlers:
  - name: Перезапустить Nginx
    service:
      name: nginx
      state: restarted
```

## 2. Балансировщики Nginx, HAProxy

С Nginx знаком как с веб-сервером, reverse proxy и балансировщиком. Он может принимать HTTP/HTTPS-запросы и проксировать их на backend-сервисы.

HAProxy - специализированный балансировщик TCP/HTTP, часто используется для высоконагруженных схем и балансировки на 4/7 уровнях.

Базовая идея балансировки:
- есть один вход;
- за ним несколько backend-серверов;
- балансировщик распределяет запросы между ними;
- дополнительно может делать health-check, TLS termination, retries, timeouts.
